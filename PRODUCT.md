# Credit Decision Committee

Мультиагентная система принятия кредитных решений для банка.

## Проблема

Банк получает заявку на кредит. Одна ML-модель даёт score, но решение всё равно остаётся «чёрным ящиком»: андеррайтер вручную сверяет политику, БКИ, доход и исключения. Это долго, дорого, плохо объясняется клиенту и плохо проходит аудит.

Типичные боли:

- модель и кредитная политика живут отдельно — решения расходятся;
- отказ/одобрение трудно обосновать регулятору и клиенту;
- серая зона всегда уходит к человеку без структурированного контекста;
- нет единого протокола: кто и на каком основании «проголосовал».

## Решение

**Credit Decision Committee** — мультиагентный «кредитный комитет» в коде.

FastAPI принимает заявку → LangGraph запускает комитет специализированных агентов → на выходе:

- решение: `approve` / `reject` / `manual_review` / `needs_info`;
- рекомендованный лимит и (опционально) ставка;
- цитаты кредитной политики;
- SHAP-факторы модели риска;
- протокол голосования агентов;
- what-if: минимальные изменения, которые меняют исход.

Модель считает риск. Политика остаётся детерминированным hard-stop. LLM не рисует score — только объясняет и собирает memo.

## Ценность для банка


| Для кого          | Что даёт                                                          |
| ----------------- | ----------------------------------------------------------------- |
| Андеррайтинг      | Меньше рутины, готовый досье-пакет по серой зоне                  |
| Риск              | Единый PD + объяснимость (SHAP) + audit trail                     |
| Compliance        | Каждое решение опирается на пункты политики                       |
| Клиентский сервис | Понятный отказ и контрфакты («что изменить»)                      |
| IT / Data Science | API-first пайплайн, агенты с разными ролями, не монолитный промпт |


## Агенты


| Агент                   | Роль             | Что делает                                                        | Стек                      |
| ----------------------- | ---------------- | ----------------------------------------------------------------- | ------------------------- |
| **Intake**              | Приёмка          | Валидация полей, нормализация фичей, флаг нехватки данных         | Pandas, Pydantic, FastAPI |
| **Risk Model**          | Риск             | Считает PD/score, отдаёт топ-факторы                              | CatBoost / sklearn, SHAP  |
| **Policy RAG**          | Compliance       | Ищет релевантные правила банка (лимиты, запреты, исключения)      | Qdrant, эмбеддинги        |
| **Fraud / Consistency** | Антифрод         | Ловит противоречия: доход vs профессия, регион vs адрес, аномалии | Правила + sklearn         |
| **Advocate**            | Защитник клиента | Ищет смягчающие факторы (зарплатный клиент, история в банке)      | RAG + эвристики           |
| **Chair**               | Председатель     | Сводит голоса, применяет hard-stop, пишет decision memo           | LangGraph                 |
| **Explain**             | Объяснение       | Текст для клиента/аудита + what-if                                | SHAP + LLM                |


Опционально позже: **Macro** (`statsmodels` / `arch`) — корректировка порогов в кризисном режиме рынка.

## Процесс принятия решения

```
                    ┌─────────────┐
                    │   Intake    │
                    └──────┬──────┘
                           │
              данные неполные → needs_info (пауза / HITL)
                           │
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
     Risk Model      Policy RAG     Fraud/Consistency
           │               │               │
           └───────────────┼───────────────┘
                           ▼
                      Advocate
                           ▼
                        Chair
                     /     |     \
              approve   reject   manual_review
                           │
                        Explain
                     (+ what-if)
```

1. **Intake** — проверка заявки; при дырах в данных → `needs_info`.
2. Параллельно: **Risk Model**, **Policy RAG**, **Fraud**.
3. **Advocate** читает выводы и спорит, если отказ «на грани».
4. **Chair**:
  - hard reject из политики (например, просрочка 90+ / PTI выше порога) → сразу `reject`;
  - иначе правила эскалации / голосование;
  - серая зона → `manual_review`.
5. **Explain** формирует memo и контрфакты.

## API (контракт)


| Метод  | Путь                          | Описание                                   |                  |
| ------ | ----------------------------- | ------------------------------------------ | ---------------- |
| `POST` | `/applications`               | Подать заявку                              |                  |
| `GET`  | `/applications/{id}`          |                                            | Статус и решение |
| `GET`  | `/applications/{id}/protocol` | Голоса агентов, цитаты политики, SHAP      |                  |
| `POST` | `/applications/{id}/what-if`  | Контрфактические сценарии                  |                  |
| `POST` | `/applications/{id}/resume`   | Дослать недостающие документы и продолжить |                  |

## Почему мультиагентность, а не один промпт

- **PD считает модель** — детерминированно и воспроизводимо.
- **Hard-rules политики** не зависят от температуры LLM.
- **Агенты имеют конфликт интересов** (Risk vs Advocate) — это имитация реального комитета.
- **Протокол** — артефакт для аудита, а не «модель так сказала».
- LLM только **объясняет** и упаковывает решение, не подменяет скоринг.

## Технологический стек


| Слой                | Технологии                                                |
| ------------------- | --------------------------------------------------------- |
| API                 | FastAPI                                                   |
| Оркестрация агентов | LangGraph                                                 |
| Табличный ML        | Pandas, NumPy, CatBoost / Scikit-learn                    |
| Объяснимость        | SHAP                                                      |
| Политика / RAG      | Qdrant, эмбеддинги (Transformers / sentence-transformers) |
| Опционально LLM     | Transformers, PEFT (доменный адаптер под язык банка)      |
| Опционально macro   | statsmodels, arch                                         |
| Инструменты агента  | MCP (`search_policy`, `run_model`, `compute_shap`, …)     |


## MVP (ориентир: ~2 недели)

1. Синтетический датасет заявок + обученный CatBoost + SHAP.
2. Кредитная политика (документы) в векторном индексе (Qdrant / аналог).
3. Граф из 4 агентов: Intake → Risk → Policy → Chair.
4. FastAPI: решение + протокол.
5. Демо-кейс: **хороший ML-score, но reject из‑за политики** — чтобы была видна ценность Policy RAG.

## Критерии успеха

- Доля заявок с автоматическим решением без потери качества риска.
- 100% reject/approve с hard-правилами имеют ссылку на пункт политики.
- Серая зона приходит к человеку с готовым протоколом (не «сырой» заявкой).
- What-if даёт хотя бы один реалистичный путь улучшения для пограничных отказов.
- Latency и стоимость вызова агентов предсказуемы (fast path vs deep path).
